검증일: 2026-09-19. Windows 환경의 Node.js 24.19.0, pnpm 11.19.0으로 점검했습니다. 실제 사용자 DB·API Key·개인 환경 파일·작업용 컴파일 산출물은 제출 소스에 포함하지 않습니다.

## 이름·나이·UL·삭제 동작 변경분

## 외부 배포 준비 추가 검증

2026-09-19에 서버의 보호 페이지 접근 검사와 세션 처리 회귀 검사를 추가하고 **전체 62개 테스트를 다시 통과**했습니다. `tests/worker.test.ts`의 6개는 이 합계에 포함됩니다. 운영 URL·시크릿 검증, 인증 헤더와 리다이렉트 차단, 집계만 로그에 출력, 느린 스캔 비중첩, HTTP/네트워크 오류 재시도, 타임아웃, 종료 시 요청 취소를 확인했습니다. 최종 운영 빌드와 TypeScript 검사도 통과했습니다.

이 환경의 Node.js 24에서는 `node --test --experimental-test-isolation=none tests/worker.test.ts`로 자식 프로세스 없이 직접 실행했습니다. 일반 환경에서는 기존 `pnpm test`에 자동 포함됩니다. 외부 네트워크나 실제 메일을 사용하는 테스트가 아닙니다.

[GitHub 저장소](https://github.com/june-young19/haru-nutri)는 생성되었습니다. Railway 웹 서비스, `/app/data` 영구 볼륨, 8개 환경변수를 준비했고 전체 소스 업로드와 실제 배포를 진행 중입니다. 공개 URL의 회원가입·DB 영속성·자동 알림을 완료로 표시하려면 배포 후 별도 검증이 필요합니다. 현재 배포 절차는 [DEPLOYMENT.md](DEPLOYMENT.md)에 있습니다.

확장된 HTTP 통합 검사는 독립 DB와 capture 모드에서 모두 통과했습니다. 원래 7개 그룹의 마지막 그룹을 확장해 비로그인·만료·로그아웃 세션의 보호 페이지 접근 제한, 계정 A/B의 제품과 보호자 정보 분리, 삭제 상태 유지, DB 오류가 잘못된 로그인 오류 대신 서버 오류로 처리되는 동작을 포함합니다. 그룹 수를 추가 테스트 개수와 혼동해 늘려 표시하지 않습니다.

## 브라우저에서 직접 확인한 순서

1. 이름·만 나이 20세로 회원가입.
2. 종합비타민의 C 100mg·D 20μg과 별도 Vitamin D 25mcg을 등록하고, 저장 전 두 제품 합계 45μg 확인.
3. 별도 입력에서 총량 145μg의 초과 미리보기 확인. 확인 체크 전 저장 비활성, 체크 후 활성, 입력 변경 후 재검사 요구 확인.
4. 최종 등록량을 45μg으로 저장하고 성분 분석 화면과 대조.
5. 두 제품 모두 복용 완료 후 비타민 D 제품 삭제. 오늘 항목 1개, 새로고침 후 유지, 분석 합계 20μg·중복 0개 확인.
6. 복용 기록 화면에서 삭제된 제품의 완료 이력 보존 확인.
7. 이름·나이를 21세로 수정하고 재조회 후 유지 확인.
8. 로컬 알림을 점검해 남아 있는 제품만 대상으로 한 알림 1개 생성 확인.
9. 만 3세로 프로필을 바꾸고 예시 초안의 아연 10mg이 연령별 UL 7mg을 초과해 확인이 필요한 흐름을 확인.
10. 만 20세로 되돌린 후 모바일에서 로그아웃·재로그인하고 오늘 항목 1개 및 삭제 상태 유지 확인.

대시보드의 예시 버튼은 제품 3개를 자동으로 만드는 방식에서 **종합비타민 초안 → 공통 성분 검사·확인 → 저장** 흐름으로 변경했습니다. 따라서 어린 연령의 UL을 초과하는 예시도 확인 절차를 거칩니다.

## 실제 이메일 검증

사용자가 허용한 본인 가입 이메일을 대상으로 실제 알림 엔진을 통해 **Resend 이메일 1통**을 발송했습니다. 공급자 API 요청 접수와 Resend 대시보드의 **`Delivered` 상태**를 확인했습니다. **사용자 받은편지함에서 직접 도착을 확인하는 단계는 아직 완료하지 않았습니다.**

초기 시연은 `capture`로 수행했으며, 현재 배포 준비 설정은 `resend`입니다. 이전 키를 제거한 뒤 로컬 비공개 환경 파일에 새 키를 설정했고 이전 키와 다름을 확인했습니다. **새 키를 이용한 외부 발송은 아직 수행하지 않았습니다.** 이전 `Delivered` 검증을 새 키·새 배포의 검증으로 해석하지 않습니다. 수신 이메일 주소·API Key·공급자 메시지 ID는 이 문서와 제출 소스에 기록하지 않습니다. `.env.example`에는 요청한 `EMAIL_MODE=resend` 및 빈 키·발신자 자리만 있습니다.

자동화 테스트는 실제 메일을 보내지 않습니다. capture 본문·수신자·상태·중복 방지·보호자 동의를 검증하고, Resend 성공·실패·불확실한 응답·재시도 경로는 모의 HTTP 응답으로 별도 검증합니다.

## 환경 제약과 재현 방법

이 실행 환경에서는 Node 자식 프로세스 생성이 `spawn EPERM`으로 제한되어 표준 `pnpm test`가 그대로 실행되지 않습니다. 따라서 동일한 테스트 소스를 작업용 폴더에 컴파일한 후 Node 테스트 러너의 프로세스 격리를 끄고 **전체 62개를 실행해 통과**했습니다. 실제 HTTP 테스트는 같은 `tests/integration.ts`의 검증 본문을 별도로 시작한 Next 운영 서버와 독립 DB에 연결해 실행했습니다. 이 과정에서 테스트용 파일을 제출 폴더에 추가하지 않았습니다.

이 환경에서는 설치 시 esbuild postinstall을 생략하는 우회를 사용했습니다. 일반 PC의 표준 설치·실행 안내와 구분하며, 이 제약을 이유로 타입 검사나 테스트 본문의 검증을 생략하지 않았습니다.

일반 개발 PC와 GitHub CI에서는 README의 `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm build` 명령을 사용합니다. 통합 테스트는 포트 3101에서 자체 개발 서버와 임시 DB를 생성·정리하므로 같은 프로젝트의 개발 서버를 먼저 종료하세요.

빌드 설정은 TypeScript API와 worker threads를 사용하고 Webpack으로 일관되게 컴파일합니다. 검사를 끄거나 TypeScript 오류를 무시하지 않습니다.

운영 시작 스크립트에서 점검한 경로는 `/`, `/signup`, `/login`, `/dashboard`, `/supplements/new`, `/duplicates`, `/history`, `/settings`, `/settings/guardian`, `/api/health`, `/icon.svg`입니다. 최초 점검의 HTTP 200은 당시 라우트 제공 확인입니다. 이후 서버 인증 보호를 추가했으므로 현재 보호 페이지는 비로그인 요청에서 로그인으로 이동해야 하며, 모든 경로가 비로그인 상태에서 HTTP 200이라고 해석하지 않습니다. 최신 접근 제한·세션·로그인·저장 동작은 별도 HTTP 통합 검사로 확인했습니다.

최초 소스 검증 당시 프로젝트와 부모 폴더에는 Git 이력이 없었습니다. 당시 제출 소스와 ignore 규칙을 검사했으며, 이후 만든 GitHub 저장소에 업로드할 때도 개인 `.env`·DB·백업을 제외해야 합니다. 최초 검사를 이후 원격 커밋 전체의 검증으로 해석하지 않습니다.

## 아직 확인하지 않은 외부 항목

- 실제 이메일의 사용자 받은편지함·스팸함 확인은 미완료입니다. 공급자 `Delivered`를 사용자 열람 확인으로 해석하지 않습니다.
- Docker 실행기가 없어 컨테이너 실행을 직접 검증하지 않았습니다. Dockerfile·Compose·영구 디스크 경로를 구성하고 소스와 대조했습니다.
- GitHub 원격 저장소와 Railway 웹·영구 볼륨·환경변수는 준비되었으며 전체 소스 업로드와 호스팅 배포는 진행 중입니다. 공개 서비스 URL 검증은 아직 완료하지 않았습니다.
- 교체한 새 Resend 키를 이용한 외부 이메일 발송은 아직 수행하지 않았습니다.

`capture`는 외부 발송이 아닙니다. 앱의 `sent`는 Resend의 API 요청 접수이며 사용자 받은편지함 확인은 아닙니다. 배포 시 발신 도메인·수신자·HTTPS·영구 디스크·워커 설정을 다시 점검하세요.
