이번 변경분은 코드·로컬 검증·원격 CI·실제 배포까지 완료했습니다. 동일 테스트 소스를 컴파일한 러너에서 도메인·UL·서버·공급자 65개를 실행했고 워커 8개를 별도로 통과해 총 73개입니다. capture HTTP 검사는 별도 3101 서버에서 수행했으며 실제 Brevo 요청을 보낸 검사가 아닙니다. 현재 환경의 자식 프로세스 제한 우회는 아래 설명과 같습니다. 전환 전 62개 기록은 과거 결과로 구분해 보존합니다.

Brevo 커밋 `a711e5d9cbb04553d7dfff848cc0b407fbdd50db`의 [GitHub Actions](https://github.com/june-young19/haru-nutri/actions/runs/35427479462)에서 표준 `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm build`가 모두 성공했습니다. Railway 웹과 워커가 같은 커밋으로 ACTIVE인 상태를 확인했습니다.

전환 후 공개 HTTPS 검사 3개 그룹을 통과했습니다. 기존 테스트 계정 2개의 데이터가 유지되었고, 별도의 새 계정 2개는 본인 알림을 끈 상태에서 가입했습니다. 복수 성분을 가진 제품의 비타민 D 20+25=45μg 합산과 제품별 비타민 C 100mg, 저장·복용 완료·삭제 이력·보호자 정보의 계정 분리·로그아웃/재로그인을 확인했습니다. 기존 사용자 개인정보는 문서에 기록하지 않습니다.

Railway 웹의 실제 Restart를 실행해 2026-09-19 15:54:41 KST 재기동 로그를 확인했습니다. 이어 공개 HTTPS 보존 검사가 성공 종료하여 Brevo 검증용 A/B 계정의 기존 세션·프로필·보호자 정보 분리·활성 제품·삭제 제품 완료 이력이 유지됨을 확인했습니다.

공개 모바일 `/settings`의 실제 446px viewport에서 이름·나이·이메일 카드, Brevo 이메일 발송 안내와 저장 버튼을 육안으로 확인했습니다. DOM의 viewport 너비와 scrollWidth가 모두 446px여서 가로 넘침이 없었습니다. 사용자 설정은 변경하지 않았고 30분 유예 시간을 유지했습니다. 이번 확인은 설정 화면만의 범위이며 모든 페이지를 새로 모바일 검증했다는 뜻은 아닙니다.

Brevo 계정의 전화·이메일 인증과 Gmail Sender Verified를 확인하고 사용자가 API Key를 Railway 비밀 변수로 등록했습니다. 확인한 발신자를 웹에 적용해 재배포했고 웹·워커 모두 ACTIVE인 상태에서 자동 발송했습니다. 설정 전의 HTTP 503은 키 누락을 숨기지 않는 동작을 확인한 과거 검사이며 현재 상태가 아닙니다. 실제 발송 결과는 아래에 구분합니다.

## 전환 전 외부 배포와 추가 검증

2026-09-19에 서버의 보호 페이지 접근 검사와 세션 처리 회귀 검사를 추가하고 **전체 62개 테스트를 다시 통과**했습니다. `tests/worker.test.ts`의 6개는 이 합계에 포함됩니다. 운영 URL·시크릿 검증, 인증 헤더와 리다이렉트 차단, 집계만 로그에 출력, 느린 스캔 비중첩, HTTP/네트워크 오류 재시도, 타임아웃, 종료 시 요청 취소를 확인했습니다. 최종 운영 빌드와 TypeScript 검사도 통과했습니다.

이 환경의 Node.js 24에서는 `node --test --experimental-test-isolation=none tests/worker.test.ts`로 자식 프로세스 없이 직접 실행했습니다. 일반 환경에서는 기존 `pnpm test`에 자동 포함됩니다. 외부 네트워크나 실제 메일을 사용하는 테스트가 아닙니다.

[GitHub 저장소](https://github.com/june-young19/haru-nutri)에 전체 소스 46개 파일을 업로드했습니다. 커밋 `141bce44b2299a5267aa7a0bf06a12c18e73c288`의 [GitHub Actions CI](https://github.com/june-young19/haru-nutri/actions/runs/35424692457)는 **성공**입니다. 표준 `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, `pnpm build` 단계가 모두 성공한 것을 원격으로 확인했습니다.

Railway의 웹 `haru-nutri`와 워커 `haru-reminders`는 ONLINE이며 실제 클라우드 Docker 빌드와 실행에 성공했습니다. 웹에는 500MB 볼륨을 `/app/data`에 연결했습니다. 실제 서비스는 [https://haru-nutri-production.up.railway.app](https://haru-nutri-production.up.railway.app)입니다. 배포 절차는 [DEPLOYMENT.md](DEPLOYMENT.md)에 있습니다.

공개 HTTPS 주소에서 별도 검증 **3개 그룹을 모두 통과**했습니다. 테스트 계정 A/B의 본인 알림을 끈 상태에서 실제 가입, 비타민 D 20+25=45μg 미리보기·저장, 복용 완료, 제품 삭제 후 이력 보존, 제품·보호자 정보의 계정 간 격리, 로그아웃 세션 무효화와 재로그인을 확인했습니다. 이 검사는 운영 서비스에서 실행되었으며 기존 사용자 정보를 변경하지 않았습니다.

실제 브라우저에서는 공개 랜딩·가입 페이지, 사용자의 직접 가입, 설정의 실제 이메일 모드 표시, 테스트 제품 등록과 대시보드 반영을 확인했습니다. 390px 화면에서 대시보드·설정의 가로 넘침이 없었고 로그아웃 버튼도 시각적으로 확인했습니다. 사용자의 개인 이름·나이·이메일은 이 문서에 기록하지 않습니다.

Railway 웹 서비스를 실제로 Restart하여 2026-09-19 14:54:26에 같은 볼륨이 다시 마운트되고 14:54:32에 Ready가 되는 로그를 확인했습니다. 재시작 후 공개 HTTPS 검사에서 기존 A/B 세션, 프로필, 보호자 정보의 계정 간 격리, 활성 제품, 삭제한 제품과 활성 제품의 완료 이력이 **모두 유지**되는 것을 확인했습니다. 영구 볼륨을 설정했다는 사실과 실제 보존 검증을 구분해 수행했습니다.

전환 전 워커의 연속된 정상 검사 주기와 같은 알림을 반복 생성하지 않는 동작을 확인했습니다. 이 결과를 새 공급자의 API·멱등성·전달 동작 검증으로 간주하지 않습니다.

확장된 HTTP 통합 검사는 독립 DB와 capture 모드에서 모두 통과했습니다. 원래 7개 그룹의 마지막 그룹을 확장해 비로그인·만료·로그아웃 세션의 보호 페이지 접근 제한, 계정 A/B의 제품과 보호자 정보 분리, 삭제 상태 유지, DB 오류가 잘못된 로그인 오류 대신 서버 오류로 처리되는 동작을 포함합니다. 그룹 수를 추가 테스트 개수와 혼동해 늘려 표시하지 않습니다.

## 브라우저에서 직접 확인한 순서

추가로 같은 로컬 브라우저에서 A 계정 전용 제품을 저장한 뒤 설정에서 로그아웃했습니다. 뒤로가기는 `/login`을 유지했고 `/dashboard` 직접 접근도 `/login`으로 이동했습니다. 이어서 B 계정으로 신규 가입하자 B의 이름·오늘 0건이 표시되고 A의 제품은 보이지 않아, 실제 화면에서도 로그아웃과 계정 분리를 확인했습니다.

1. 이름·만 나이 20세로 회원가입.
2. 종합비타민의 C 100mg·D 20μg과 별도 Vitamin D 25mcg을 등록하고, 저장 전 두 제품 합계 45μg 확인.
3. 별도 입력에서 총량 145μg의 초과 미리보기 확인. 확인 체크 전 저장 비활성, 체크 후 활성, 입력 변경 후 재검사 요구 확인.
4. 최종 등록량을 45μg으로 저장하고 성분 분석 화면과 대조.
5. 두 제품 모두 복용 완료 후 비타민 D 제품 삭제. 오늘 항목 1개, 새로고침 후 유지, 분석 합계 20μg·중복 0개 확인.
6. 복용 기록 화면에서 삭제된 제품의 완료 이력 보존 확인.
7. 이름·나이를 21세로 수정하고 재조회 후 유지 확인.
8. 로컬 알림을 점검해 남아 있는 제품만 대상으로 한 알림 1개 생성 확인.
9. 만 3세로 프로필을 바꾸고 예시 초안의 아연 10mg이 연령별 UL 7mg을 초과해 확인이 필요한 흐름을 확인.
10. 만 20세로 되돌린 후 모바일에서 로그아웃·재로그인하고 오늘 항목 1개 및 삭제 상태 유지 확인.

대시보드의 예시 버튼은 제품 3개를 자동으로 만드는 방식에서 **종합비타민 초안 → 공통 성분 검사·확인 → 저장** 흐름으로 변경했습니다. 따라서 어린 연령의 UL을 초과하는 예시도 확인 절차를 거칩니다.

## 실제 Brevo 자동 이메일 검증

2026-09-19 한국 시간 기준입니다. 1차 학교 이메일 검사와 2차 별도 Gmail 검사를 구분합니다. **총 6통 모두 실제 Railway 워커의 자동 주기로 발송되어 API 접수와 Brevo `Delivered`를 확인했습니다.** preview나 cron API를 직접 호출하지 않았으며 캡처로 대체하지 않았습니다. 사용자 실제 수신 확인은 A1·B2·C2의 세 건입니다.

| 검사·대상                      | 워커·앱 결과                                                       | Brevo 결과      | 수신자 확인                               |
| ------------------------------ | ------------------------------------------------------------------ | --------------- | ----------------------------------------- |
| 1차 A1 — 본인 Gmail            | 16:02:44 `checked=1`, `sent=1`, `captured=0`, `failed=0`           | 16:02 Delivered | 기본 받은편지함 수신 확인                 |
| 1차 B1 — 학교 이메일 일반 알림 | 16:07:23 자동 발송, 앱 sent·공급자 식별자 저장                     | 16:07 Delivered | Outlook에서도 찾지 못함. 실제 수신 미확인 |
| 1차 C1 — 학교 이메일 보호자    | 16:08:24 본인 알림 이후 동의·임시 추가 유예 5분을 거쳐 sent        | 16:08 Delivered | Outlook에서도 찾지 못함. 실제 수신 미확인 |
| 2차 A2 — 본인 선행 알림        | 16:16:26 B2와 함께 `checked=2`, `sent=2`, `captured=0`, `failed=0` | 16:16 Delivered | 별도 수신 확인을 요청하지 않음            |
| 2차 B2 — 별도 Gmail 일반 알림  | 16:16:26 A2와 같은 주기에서 자동 발송                              | 16:16 Delivered | 사용자 실제 수신 확인. 분류 폴더 미확인   |
| 2차 C2 — 해당 Gmail 보호자     | 앱 16:21:26 sent, 워커 16:21:27 sent=1. 동의·추가 유예 5분 적용    | 16:21 Delivered | 사용자 기본 받은편지함 수신 확인          |

학교 B1/C1은 사용자가 Outlook에서도 찾지 못했으며 원인은 확인되지 않았습니다. 이 두 건은 실제 수신 성공으로 표시하지 않습니다. 이후 별도 Gmail B2/C2에서 일반 알림·보호자 알림의 실제 수신을 확인했습니다. Brevo의 Opened 이벤트는 사용자의 직접 확인을 대신하는 근거로 사용하지 않았습니다. 특정 학교·개인 주소는 기록하지 않습니다.

무료 Gmail 발신자는 로그에서 `*.brevosend.com` 주소로 대체됐고 Reply-To는 원래 등록 주소였습니다. 공식 트랜잭션 문서의 예시인 `*.t-sender-sib.com`과 다를 수 있어 실제 관찰 결과를 기록합니다. 개인 주소·계정 번호·공급자 식별자는 공개하지 않습니다.

워커 재배포 후 A1의 동일 알림 추가 발송이 없었고, 2차 C2 이후에도 16:25까지 `sent=0`을 확인했습니다. 1차 정리 후 16:10:25 대상이 0이 된 뒤 별도 2차 일정을 만들었으므로 A2는 A1의 중복 발송이 아닙니다.

최종적으로 임시 보호자 설정은 알림 끄기·주소 비우기·추가 유예 120분으로 복원하고 A2/C2 테스트 제품을 UI에서 삭제해 빈 목록을 확인했습니다. 외부 B1/B2 계정은 본인·보호자 알림을 끄고 주소 비우기·120분 복원·제품 보관·로그아웃을 완료했습니다. 본인 유예 시간은 전체 검사 중 30분을 유지했습니다. **16:26:28 최종 워커는 `mode=brevo`, `checked=0`, `sent=0`, `captured=0`, `failed=0`, `skipped=0`**으로 검사 종료 후 알림 대상이 없음을 확인했습니다.

API 접수는 수신함 도착이 아닙니다. 공급자 `Delivered` 역시 수신 서버 전달 상태이며 사용자가 읽었다는 뜻은 아닙니다. 이메일 주소·API Key·공급자 메시지 ID·SMTP 고유 ID는 공개 기록에 넣지 않습니다. [Brevo 이벤트 안내](https://help.brevo.com/hc/en-us/articles/35699922048146-View-and-export-your-event-logs)

공급자는 `Delivered` 이후에도 기관의 수신 필터·지연 반송·스팸 분류 등으로 사용자가 찾지 못할 수 있다고 안내합니다. 학교 B1/C1의 원인이 그것이라고 확정한 것은 아닙니다. [공식 문제 해결 안내](https://help.brevo.com/hc/en-us/articles/17677373572626-FAQs-Why-emails-are-marked-delivered-but-are-not-received)

자동화 테스트의 캡처·모의 HTTP 결과와 이전 공급자의 수신 기록은 위 실제 Brevo 검증 건수에 포함하지 않습니다.

## 환경 제약과 재현 방법

이 실행 환경에서는 Node 자식 프로세스 생성이 `spawn EPERM`으로 제한되어 표준 `pnpm test`가 그대로 실행되지 않습니다. 동일한 테스트 소스를 작업용 폴더에 컴파일한 후 Node 테스트 러너의 프로세스 격리를 끄는 방식으로 실행했습니다. **전환 전 검증은 62개**, **Brevo 전환 후 검증은 동일 방식의 65개와 별도 워커 8개를 합쳐 73개**를 통과했습니다. 실제 HTTP 테스트는 같은 `tests/integration.ts`의 검증 본문을 별도 Next 서버와 독립 DB에 연결해 실행했습니다. 이 과정에서 테스트용 파일을 제출 폴더에 추가하지 않았습니다.

이 환경에서는 설치 시 esbuild postinstall을 생략하는 우회를 사용했습니다. 일반 PC의 표준 설치·실행 안내와 구분하며, 이 제약을 이유로 타입 검사나 테스트 본문의 검증을 생략하지 않았습니다.

GitHub CI에서는 위의 표준 설치·검사·테스트·빌드 명령을 실제로 모두 통과했습니다. 일반 개발 PC에서도 README의 명령을 사용합니다. 통합 테스트는 포트 3101에서 자체 개발 서버와 임시 DB를 생성·정리하므로 같은 프로젝트의 개발 서버를 먼저 종료하세요.

빌드 설정은 TypeScript API와 worker threads를 사용하고 Webpack으로 일관되게 컴파일합니다. 검사를 끄거나 TypeScript 오류를 무시하지 않습니다.

운영 시작 스크립트에서 점검한 경로는 `/`, `/signup`, `/login`, `/dashboard`, `/supplements/new`, `/duplicates`, `/history`, `/settings`, `/settings/guardian`, `/api/health`, `/icon.svg`입니다. 최초 점검의 HTTP 200은 당시 라우트 제공 확인입니다. 이후 서버 인증 보호를 추가했으므로 현재 보호 페이지는 비로그인 요청에서 로그인으로 이동해야 하며, 모든 경로가 비로그인 상태에서 HTTP 200이라고 해석하지 않습니다. 최신 접근 제한·세션·로그인·저장 동작은 별도 HTTP 통합 검사로 확인했습니다.

## 검증 범위의 제한

- Brevo 변경분은 73개 자동 테스트·7개 HTTP 그룹·TypeScript·빌드·표준 GitHub CI·웹/워커 배포·공개 기능 검사 3개 그룹이 성공했습니다. 실제 자동 메일 6통 모두 API 접수·Delivered를 확인했고 A1·B2·C2는 사용자 실제 수신도 확인했습니다. 학교 B1/C1은 실제 수신 미확인·원인 불명이며 A2는 별도 수신 확인을 요청하지 않았습니다.
