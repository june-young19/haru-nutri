# 인증·데이터·알림의 구현 범위

이 문서는 코드에서 사용하는 보호 장치와 운영 전 확인할 한계를 설명합니다. 보안 인증이나 의료기기 적합성 평가를 받은 서비스라는 의미는 아닙니다.

## 계정과 로그인

- 이메일·이름·나이·비밀번호 입력은 서버에서도 검사합니다. 비밀번호 길이는 10~128자이며 신규 가입 나이는 1~120의 정수입니다.
- 비밀번호는 사용자별 임의 salt와 Node.js `scrypt`로 해시합니다. 원문 비밀번호를 DB에 저장하거나 API 응답으로 내보내지 않습니다.
- 로그인 세션 토큰은 암호학적으로 안전한 난수로 만들고, DB에는 토큰의 SHA-256 해시만 저장합니다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 사용하며 운영 모드에는 `Secure`를 추가합니다. 만료 기간은 7일입니다. 로그아웃 시 서버 세션을 제거합니다.
- 회원가입·로그인 시도 제한은 DB에 저장하므로 서버가 다시 시작되어도 즉시 초기화되지 않습니다. 기본 `TRUST_PROXY=false`에서는 IP 헤더를 신뢰하지 않아 일부 제한 버킷을 모든 접속자가 공유합니다. 신뢰하는 운영 프록시가 클라이언트 제공 IP 헤더를 덮어쓸 때만 `TRUST_PROXY=true`로 바꿉니다.
- 브라우저의 상태 변경 요청은 Origin과 cross-site 요청 여부를 검사합니다. 다른 출처를 임의로 허용하는 CORS 설정은 하지 않습니다.

가입 시 이메일 소유권 확인과 MFA는 아직 제공하지 않습니다. 비밀번호 재설정 시에는 이메일 인증코드로 해당 메일 접근을 확인하지만, 이를 모든 가입자의 이메일이 확인되었다는 뜻으로 설명하지 않습니다.

## 비밀번호 재설정

`/forgot-password`에서 요청·코드 확인·새 비밀번호 저장을 순서대로 수행합니다. 기존 Brevo provider를 재사용하며 `capture`에서 가짜 인증코드를 보여주지 않습니다. 이번 기능의 실제 운영 발송·사용자 비밀번호 변경 검증은 [검증 기록](VERIFICATION.md)에서 별도로 확인합니다.

- 요청은 가입 여부와 관계없이 같은 HTTP 202와 중립적인 **요청 접수** 안내를 반환합니다. 알려진·알려지지 않은 이메일 모두 같은 암호화 작업과 큐 형식을 사용합니다. 메일 발송 성공이라고 표시하지 않습니다.
- 실제 전송은 응답 후 Next.js `after`에서 저장된 큐를 처리합니다. 기존 cron handler도 남은 요청을 회수하므로 별도 워커 서비스를 만들지 않습니다.
- 6자리 숫자는 `crypto.randomInt`로 생성하며 유효시간은 10분입니다. salt를 포함한 scrypt 해시만 저장합니다. 원문 코드·변경 토큰은 DB·알림 내역·URL·응답 본문·localStorage에 저장하지 않습니다.
- 이메일별 재요청은 60초 대기·시간당 최대 5회, IP별 요청은 시간당 20회로 제한합니다. 코드 검증은 요청당 최대 5회 실패 시 무효화하고 IP당 15분 100회 제한도 적용합니다. 새 요청은 이전 코드·권한을 무효화합니다.
- 코드 확인 뒤에는 5분짜리 일회용 변경 권한을 HttpOnly·SameSite=Lax 쿠키로 전달합니다. 운영은 Secure, 경로는 `/api/auth/password-reset`으로 제한하며 DB에는 토큰 해시만 남깁니다.
- 회원가입·로그인·로그아웃 시에도 같은 경로의 재설정 권한 쿠키를 지웁니다. 한 브라우저에서 계정을 바꾸거나 로그아웃한 뒤 이전 변경 권한 쿠키가 남지 않도록 처리합니다.
- 완료 시 새 비밀번호 해시 저장·해당 계정의 모든 세션 제거·다른 재설정 코드와 권한 무효화를 하나의 트랜잭션에서 수행합니다. 자동 로그인하지 않으며 새 비밀번호로 다시 로그인해야 합니다.
- Brevo 설정 누락·`capture` 등 계정과 무관한 전역 오류는 모든 이메일에 동일하게 503을 반환합니다. 개별 전송 실패는 공개 요청 응답으로 계정 존재를 드러내지 않고 서버에 민감정보 없는 실패를 기록하며 코드를 무효화합니다. 실패한 이메일은 자동 재전송하지 않습니다.
- 60초 넘게 미완료인 전송 작업은 불확실한 상태로 실패 처리해 자동으로 다시 보내지 않습니다. 운영자는 접수 응답만 보고 전달을 단정하지 말고 공급자 상태와 실제 메일함을 확인합니다.

API는 `POST /api/auth/password-reset/request`의 `{email}`, `/verify`의 `{email,requestId,code}`, `/complete`의 `{password,passwordConfirm}`과 변경 권한 쿠키를 사용합니다. request의 202는 `requestId`, 유효시간, 재요청 대기와 접수 문구만 반환합니다. `/verify`의 성공도 인증코드나 토큰 원문을 JSON으로 내보내지 않습니다. 스키마 버전 4는 `password_reset_requests`와 인덱스를 추가하며 기존 계정 데이터를 초기화하지 않습니다.

## 사용자별 데이터 분리

브라우저가 보낸 사용자 ID를 신뢰하지 않고, 세션에서 사용자 ID를 구합니다. 영양제·일정·기록·설정·알림 조회와 변경 시 해당 ID로 소유권을 검사합니다. 자식 테이블은 소유한 영양제나 일정을 통해 연결해 검증합니다. 계정 A가 계정 B의 제품 ID를 알아도 조회·수정·복용 체크를 할 수 없어야 합니다.

SQL은 바인딩 매개변수를 사용합니다. 외래 키, 일정·날짜별 완료 기록의 유일성 제약, 알림 대상별 유일성 제약을 DB에서도 유지합니다. DB 파일은 서버 전용이며 `public/`에 놓지 않습니다. `.gitignore`와 `.dockerignore`에서 환경 파일·DB를 제외합니다.

일정 변경 시 기존 완료 기록을 지워서 비율을 바꾸는 방식으로 처리하지 않습니다. 일정의 적용 날짜와 제품 스냅샷을 보관합니다. 자세한 적용 시점은 저장 후 화면 안내를 기준으로 확인합니다.

제품 삭제는 보관 처리입니다. 해당 제품은 오늘의 일정·진행률·활성 성분 분석·새 알림에서 빠지고 기존 완료 기록은 읽기 전용으로 남습니다. 제품 삭제는 계정 전체의 개인정보 삭제 기능이 아닙니다.

## 회원 탈퇴와 보관 범위

회원 탈퇴는 설정의 위험 영역에서 `/settings/delete-account`로 이동해 삭제 범위 안내 → 현재 비밀번호 재입력 → 최종 확인 체크와 버튼을 거칩니다. 이번 추가 작업의 테스트·운영 반영 상태는 [검증 기록](VERIFICATION.md)과 구분해 확인합니다. 삭제 대상은 서버가 인증한 현재 세션의 사용자이며 클라이언트의 임의 사용자 ID로 정하지 않습니다. 기존 Origin 검사와 서버 scrypt 검증을 적용합니다.

비밀번호 확인으로 발급하는 변경 권한은 5분짜리이며 현재 사용자·세션·비밀번호 상태에 연결됩니다. 쿠키는 HttpOnly·SameSite=Lax, 운영 Secure, `/api/account/deletion` 경로를 사용합니다. 최종 요청에서도 유효한 현재 세션·권한·비밀번호 상태와 명시적 확인을 재검사합니다. 계정별 확인 5회/15분, IP별 확인 20회/15분 및 완료 요청 30회/15분 제한을 적용합니다. 취소·만료·세션 종료 후 같은 권한을 재사용하는 흐름을 허용하지 않습니다.

| 데이터                                                      | 탈퇴 처리                                                                                                                                      |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`                                                     | 이메일·이름·나이·비밀번호 해시·온보딩·설문 응답·개인 알림 설정 삭제. 설문 결과·제품 순위는 이를 바탕으로 계산하며 별도 개인 순위 테이블은 없음 |
| `sessions`                                                  | 해당 사용자의 모든 세션 삭제                                                                                                                   |
| `supplements`, `supplement_ingredients`, `intake_schedules` | 활성 제품과 이미 보관한 제품, 모든 성분·과거/현재 일정 삭제                                                                                    |
| `intake_records`, `notification_logs`                       | 완료 이력과 발송/실패/대기/캡처를 포함한 개인 알림 내역 삭제                                                                                   |
| `guardian_settings`                                         | 보호자 이메일·활성 상태·동의 시각 삭제                                                                                                         |
| `password_reset_requests`                                   | 사용자 ID 또는 정규화 이메일 해시에 연결된 요청·코드 해시·변경 권한 삭제. 가입 전 `user_id=NULL` 요청도 이메일 해시로 찾아 삭제                |
| `account_deletion_grants`                                   | 해당 사용자의 본인 확인 권한 삭제. 세션 삭제도 외래 키 cascade로 권한을 제거                                                                   |
| `auth_attempts`                                             | 소유자 해시로 식별되는 사용자 버킷과 재구성 가능한 이메일/사용자 버킷 삭제. 공용 IP·공식 API 예산 버킷은 유지                                  |

기록·알림을 먼저 지우고 외래 키 cascade와 명시적 삭제를 하나의 트랜잭션으로 수행합니다. 실패하면 전체를 롤백하며 내부 SQL·해시·stack trace 대신 일반 오류를 반환합니다. 성공 시 현재 인증·재설정·탈퇴 쿠키를 지우고 전체 세션이 무효화됩니다. 같은 이메일 재가입은 새 계정이며 삭제된 제품·기록·설정과 연결하지 않습니다.

스키마 v5는 `account_deletion_grants`와 `auth_attempts.owner_hash`를 추가하는 방식으로 기존 사용자 데이터를 보존합니다. 신규 이메일+IP 복합 제한은 소유자 해시로 삭제할 수 있고 구버전의 현재 접속 IP 복합 버킷도 재구성해 지웁니다. 구버전에서 소유자 없이 해시만 저장한 다른 IP의 로그인 복합 버킷은 이메일만으로 역추적할 수 없습니다. 이 버킷의 제한은 최대 15분 후 만료되며, 행은 다음 요청 제한 정리 시 제거됩니다. 해시가 개인정보와 무관한 완전 익명 정보라고 주장하지 않습니다. 다른 사용자와 공유하는 IP 제한을 한 사람의 탈퇴를 이유로 모두 삭제하지 않습니다.

v4까지만 지원하는 구버전은 v5 DB에 대한 버전 검사를 통과하지 못합니다. 코드를 revert한 뒤 `user_version`만 낮추는 롤백은 지원하지 않습니다. 기능을 되돌려야 한다면 v5 호환성을 유지한 수정본을 배포해야 하며, 백업 복원은 탈퇴 이후 변경·삭제 상태를 누락할 수 있으므로 별도 운영 절차가 필요합니다. 마이그레이션 전후 데이터 보존 검사와 탈퇴 후 복원 방지는 서로 다른 검증입니다.

API는 `POST /api/account/deletion/verify`의 `{password}` → 5분 권한 쿠키, `/complete`의 `{confirmed:true}` → `{deleted:true}`, `/cancel`의 `{}` → `{cancelled:true}`입니다. 비밀번호 확인 중 비동기 해시 검증이 끝난 뒤에도 현재 세션·사용자·비밀번호 상태를 다시 조회합니다. 최종 삭제 트랜잭션에는 외부 발송이나 비동기 대기가 없으며 현재 상태가 바뀌었다면 삭제하지 않습니다.

탈퇴 완료 후 다음 알림 조회에는 계정·일정이 존재하지 않아 본인·보호자 대상에 포함되지 않아야 합니다. 이미 읽어 둔 후보도 알림 처리권 획득 트랜잭션 안에서 유효성을 다시 검사해 삭제된 사용자의 로그를 재생성하지 않으며, 실제 발송 직전에도 사용자·일정 유효성을 재검사합니다. DB 삭제와 외부 요청을 하나의 원자적 작업으로 묶지는 않습니다. 이미 외부 요청이 시작되었거나 공급자에게 접수된 메일은 회수할 수 없으므로 탈퇴 이후 실제 도착 가능성까지 없다고 보장하지 않습니다. 현재 코드는 Brevo의 `/v3/smtp/email` 트랜잭션 발송만 사용하며 Contacts 생성·저장 API를 호출하지 않습니다. 따라서 앱이 별도 Contacts를 만들었다고 가정한 삭제 요청은 추가하지 않습니다. [Brevo 발송 API](https://developers.brevo.com/reference/send-transac-email)

여기서 삭제는 **운영 DB에서 행을 제거하는 것**입니다. SQLite 파일의 재사용 공간·WAL·운영자가 만든 백업·호스팅 스냅샷의 과거 바이트가 즉시 소거된다고 보장하지 않습니다. 전용 저장장치 소거·백업 만료·Brevo 전달 로그 삭제 기능도 구현하지 않습니다. 이미 받은 메일은 수신자의 메일함에 남습니다. 백업은 접근을 제한해 별도 보관하고, 오래된 백업을 복원할 때 탈퇴한 계정·알림이 다시 활성화되지 않도록 운영자가 서비스를 열기 전에 삭제 상태를 별도로 확인해야 합니다. [SQLite 삭제 관련 설정](https://www.sqlite.org/pragma.html#pragma_secure_delete), [SQLite WAL 설명](https://www.sqlite.org/wal.html)

기존 DB의 `nickname`은 이름으로 이전하고 나이는 추정하지 않아 `NULL`로 유지합니다. 스키마 버전 2로의 변경은 트랜잭션에서 수행합니다. 업그레이드 전에 구버전 서버와 워커를 종료하고 DB 디렉터리를 백업합니다. 구버전과 신버전을 같은 DB에 동시에 연결하지 않습니다. 기존 계정·세션·섭취 정보가 남아 있는 백업은 소스 코드와 분리해 접근 권한을 관리합니다.

Brevo 전환의 스키마 버전 3은 `notification_logs`에 재시도 가능 여부를 저장하는 열을 추가합니다. 기본값은 재시도 불가이며 이전 실패를 자동 재발송하지 않습니다. 기존 알림 상태와 계정·제품·복용 기록을 지우거나 새 DB로 교체하지 않습니다.

## 공식 제품 데이터의 경계

`FOOD_SAFETY_API_KEY`는 웹 서버에서만 읽습니다. 공식 API가 키를 URL 경로에 사용하므로 완성된 요청 URL·외부 오류 본문을 사용자나 로그에 그대로 전달하지 않습니다. 요청 대상은 고정된 공식 HTTPS 호스트이며 리다이렉트를 따라가지 않습니다. 응답 크기·시간·동시 요청·시간당 호출량을 제한하고 외부 문자열을 HTML로 실행하지 않습니다.

공식 제품 응답은 사용자가 검토해야 하는 자료입니다. 함량·단위·하루 기준량이 불명확하면 추정하지 않으며 초안에서 수정한 뒤 기존 서버 중복·UL 검사를 거쳐 저장합니다. 제품명 검색 실패가 수동 등록을 막지 않습니다. 관심 정렬은 부분 검색 결과이며 회원의 전체 섭취 적정성이나 제품 안전성을 판단하지 않습니다. [제품 데이터 상세](PRODUCT_DATA.md)

## 상한량 비교의 경계

UL 자료는 공식 출처·출처 문서 개정 연도·버전·적용 연령·범위를 [기준 자료](../lib/ul-reference.ts)에서 함께 관리합니다. 저장 전에 서버에서 로그인 사용자의 등록 제품과 후보 제품을 합산하며, 수치 UL 초과가 있으면 `safetyAcknowledged: true` 없이 저장하는 요청을 거부합니다. 브라우저 경고를 숨기는 것으로 서버 검사를 우회할 수 없어야 합니다. 대시보드 예시도 편집기 초안만 채워 공통 검사·확인 과정을 거칩니다.

사용자 입력 나이가 없거나, 성분 자료가 없거나, 성분 형태·단위가 불명확하면 비교할 수 없다는 상태를 반환합니다. 상한량이 설정되지 않은 성분을 무제한 안전으로 처리하지 않습니다. UL 이하 결과와 사용자의 경고 확인은 개인의 복용 안전·적정성·의료적 승인을 의미하지 않습니다. 성별·임신·수유·질환·약물·식사 전체를 반영한 임상 판단 기능은 제공하지 않습니다.

## 이메일과 보호자 동의

- `capture` 모드는 메시지를 DB에 저장할 뿐 외부에 발송하지 않습니다. 로컬 시연에서는 이 모드를 명시적으로 설정합니다. `.env.example`의 `brevo`는 실전 설정용이며 키·발신 주소가 빈 값입니다. 캡처 내역에도 개인정보가 포함될 수 있으므로 해당 사용자만 볼 수 있습니다.
- `brevo` 모드는 서버의 `BREVO_API_KEY`, `EMAIL_FROM`, `EMAIL_FROM_NAME`을 사용합니다. 브라우저 코드와 워커에는 메일 API Key를 전달하지 않습니다. API Key와 SMTP Key는 구분합니다.
- `EMAIL_MODE` 누락·오타, 필요한 키·발신자 누락은 알림 오류로 처리합니다. 실제 API 실패도 캡처나 성공으로 바꾸지 않습니다. 회원가입·영양제 저장 기능은 메일 설정과 분리합니다.
- 본인 알림을 먼저 처리하고, 그 이후의 추가 유예 시간과 여전히 미확인인 상태를 확인한 뒤 보호자 알림을 처리합니다.
- 보호자 알림은 유효한 주소, 활성화 상태, 명시적 동의 시각이 모두 필요합니다. 주소를 바꾸면 기존 동의를 그대로 옮기지 않습니다.
- 동의 해제나 복용 완료 후 새 알림은 전송 대상에서 제외됩니다. 이미 공급자에게 전달된 이메일을 회수하는 기능은 없습니다.
- 알림 문구는 완료 체크의 부재만 안내합니다. 미복용·결핍·의료적 위험을 추론하지 않습니다.
- 발송 요청 결과와 오류는 알림 로그에 기록합니다. API 요청 수락은 받은편지함 도착 확인과 다릅니다.

공급자 대시보드의 `Delivered`도 사용자가 메일을 열어 확인했다는 의미는 아닙니다. 받은편지함·스팸함 확인과 앱의 전송 상태는 별도로 구분해 보고합니다.

Brevo 전환 후 실제 Railway 워커의 두 차례 검사에서 총 6통의 API 접수·`Delivered`를 확인했고, 그중 본인 Gmail·별도 Gmail 일반 알림·동의한 Gmail 보호자 알림은 사용자 수신도 확인했습니다. 학교 이메일 두 건은 `Delivered` 이후에도 사용자가 Outlook에서 찾지 못해 실제 수신은 미확인입니다. 각 메시지의 확인 범위는 [검증 기록](VERIFICATION.md)에 구분합니다. 이전 공급자의 기록을 재사용하지 않으며 일부 수신 성공으로 모든 주소에 전달을 보장하지 않습니다.

Brevo 발신자 확인은 발신 주소를 제어한다는 절차이며 앱 회원의 이메일 소유권 확인을 대신하지 않습니다. 무료 Gmail 발신자는 공급자에 의해 다른 From 주소로 표시될 수 있습니다. API IP 제한이 요청을 차단하면 계정의 Authorized IPs에서 해당 서버 IP를 확인한 뒤 필요한 항목만 승인합니다. [Brevo 발신자 안내](https://help.brevo.com/hc/en-us/articles/208836149-Create-a-new-sender-From-name-and-From-email), [API IP 보안](https://help.brevo.com/hc/en-us/articles/5740111683858-Authorize-and-block-IP-addresses-for-API-and-SMTP-security)

보호자 주소의 소유권을 보호자 본인에게 다시 확인하는 이중 동의 절차는 현재 제공하지 않습니다. 사용자가 보호자에게 안내 내용을 설명하고 동의를 얻은 주소를 입력해야 합니다. 운영 확대 전 수신자가 직접 구독을 거절·철회할 수 있는 기능을 추가해야 합니다.

## 예약 실행 API

`GET /api/cron/notifications`는 로그인 세션 대신 `Authorization: Bearer <CRON_SECRET>`을 검사하는 서버 작업용 경로입니다. 충분히 긴 임의 시크릿을 만들고 앱과 워커에만 전달합니다. URL 쿼리에 시크릿을 넣지 않으며 GitHub Actions YAML에 운영 시크릿을 직접 쓰지 않습니다.

워커는 URL에 자격증명·쿼리·프래그먼트가 포함된 설정을 거부하고 HTTP 리다이렉트를 따라가지 않습니다. 로그에는 처리 건수와 HTTP 상태만 남기며 응답 본문·수신자·시크릿은 기록하지 않습니다. 종료 시 진행 중 요청을 중단하고, 실패한 스캔은 다음 주기에 재시도합니다. 서버의 영구 알림 claim과 공급자 멱등성 키로 중복 처리를 제한합니다. 배포 시 두 서비스 설정은 [배포 가이드](DEPLOYMENT.md)를 참고합니다.

복용 알림 메일은 명백한 API 4xx 요청 거절만 60초 간격으로 총 3회까지 시도합니다. 네트워크 오류·5xx·중복 키 응답·성공 응답의 messageId 누락은 접수 여부가 불명확하므로 `failed`로 보존하고 자동 재발송을 중단합니다. 15분 넘게 미완료인 처리도 임의로 다시 보내지 않습니다. 공급자 로그에서 실제 접수·전달을 먼저 확인해야 합니다. 멱등성 키의 보관 기간이 지나도 무조건 재시도하는 방식은 사용하지 않습니다. 비밀번호 재설정 메일은 위의 별도 정책에 따라 실패 후 자동 재전송하지 않습니다.

로그인 사용자용 `POST /api/notifications/preview`는 해당 사용자 범위에서 시연하며 cron 권한을 대신하지 않습니다. UI 시연을 이유로 다른 사람의 계정이나 보호자 주소에 임의로 발송하지 않습니다.

이 경로도 실제 알림 엔진을 사용하므로 `brevo` 모드에서는 조건에 따라 실제 발송합니다. `capture` 모드에서 만든 본인 알림을 실전 모드로 전환해 보호자 발송의 근거로 사용하지 않습니다. 실제 본인 발송의 API 접수 상태를 확인한 뒤 보호자 조건을 평가하며 받은편지함 도착을 추정하지 않습니다.

## 데이터와 인프라

- 운영은 HTTPS, 영구 디스크, 앱 프로세스 1개를 기준으로 합니다. SQLite 파일을 여러 앱 컨테이너가 동시에 공유하는 구성과 서버리스 배포는 지원하지 않습니다.
- 워커는 DB에 직접 접근하지 않고 앱 API에 요청합니다. 따라서 웹 서버에만 영구 볼륨을 연결합니다.
- DB 파일 자체는 이 애플리케이션이 암호화하지 않습니다. 호스팅의 저장소 보호·백업 접근 권한을 운영자가 관리합니다.
- 서비스와 워커를 종료한 뒤 DB 디렉터리 전체를 백업하거나 SQLite의 일관된 백업 기능을 사용합니다. 실행 중인 DB 파일 하나만 무작정 복사하지 않습니다.
- 이메일 주소, 섭취 정보, 알림 본문이 저장됩니다. DB 백업을 공개 저장소나 발표 화면에 그대로 공개하지 않습니다.
- 시크릿 유출 시 공급자 API Key와 `CRON_SECRET`을 교체합니다. 실제 비밀번호·토큰을 이슈에 첨부하지 않습니다.
- API Key를 채팅·발표 화면·공개 로그에 노출했다면 해당 키를 폐기하고 재발급한 키를 개인 `.env` 또는 배포 서비스의 비밀 설정에만 저장합니다. `.env.example`에는 빈 자리만 유지합니다.

이전 버전에서 노출된 공급자 키의 폐기를 확인한 기록은 새 Brevo 키의 보안 검증을 대신하지 않습니다. 공급자 전환 후 사용하지 않는 이전 비밀값을 환경변수에서 제거하고 Brevo 키도 동일하게 보호합니다. 키 값·키 이름·수신자 주소·공급자 메시지 ID는 공개 문서에 기록하지 않습니다.

## 현재 제공하지 않는 기능

가입 시 이메일 소유권 확인, 이메일 자체에 접근할 수 없을 때의 계정 복구, 데이터 내보내기, 보호자 직접 수신 거부 링크, 포괄적 감사 로그, 침투 테스트, 재해 복구 자동화는 별도 개발이 필요합니다. 회원 탈퇴는 위 범위와 최신 검증 상태를 참고합니다. 구현되지 않은 보호 장치를 제공한다고 표시하지 않습니다.

문제를 제보할 때는 사용한 화면, 재현 순서, 기대 결과와 실제 결과를 적고 비밀번호·API Key·세션 쿠키·실제 복용 기록은 제외합니다.
