# 인증·데이터·알림의 구현 범위

이 문서는 코드에서 사용하는 보호 장치와 운영 전 확인할 한계를 설명합니다. 보안 인증이나 의료기기 적합성 평가를 받은 서비스라는 의미는 아닙니다.

## 계정과 로그인

- 이메일·이름·나이·비밀번호 입력은 서버에서도 검사합니다. 비밀번호 길이는 10~128자이며 신규 가입 나이는 1~120의 정수입니다.
- 비밀번호는 사용자별 임의 salt와 Node.js `scrypt`로 해시합니다. 원문 비밀번호를 DB에 저장하거나 API 응답으로 내보내지 않습니다.
- 로그인 세션 토큰은 암호학적으로 안전한 난수로 만들고, DB에는 토큰의 SHA-256 해시만 저장합니다.
- 세션 쿠키는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 사용하며 운영 모드에는 `Secure`를 추가합니다. 만료 기간은 7일입니다. 로그아웃 시 서버 세션을 제거합니다.
- 회원가입·로그인 시도 제한은 DB에 저장하므로 서버가 다시 시작되어도 즉시 초기화되지 않습니다. 기본 `TRUST_PROXY=false`에서는 IP 헤더를 신뢰하지 않아 일부 제한 버킷을 모든 접속자가 공유합니다. 신뢰하는 운영 프록시가 클라이언트 제공 IP 헤더를 덮어쓸 때만 `TRUST_PROXY=true`로 바꿉니다.
- 브라우저의 상태 변경 요청은 Origin과 cross-site 요청 여부를 검사합니다. 다른 출처를 임의로 허용하는 CORS 설정은 하지 않습니다.

이 버전은 이메일 소유권 확인, 비밀번호 재설정, MFA를 제공하지 않습니다. 입력한 이메일이 실제 본인 주소인지 서비스가 검증했다고 설명하면 안 됩니다. 공개 사용자 규모를 확대할 때는 이 흐름을 먼저 추가하고, 이메일 발송 악용을 제한하는 운영 정책을 함께 적용합니다.

## 사용자별 데이터 분리

브라우저가 보낸 사용자 ID를 신뢰하지 않고, 세션에서 사용자 ID를 구합니다. 영양제·일정·기록·설정·알림 조회와 변경 시 해당 ID로 소유권을 검사합니다. 자식 테이블은 소유한 영양제나 일정을 통해 연결해 검증합니다. 계정 A가 계정 B의 제품 ID를 알아도 조회·수정·복용 체크를 할 수 없어야 합니다.

SQL은 바인딩 매개변수를 사용합니다. 외래 키, 일정·날짜별 완료 기록의 유일성 제약, 알림 대상별 유일성 제약을 DB에서도 유지합니다. DB 파일은 서버 전용이며 `public/`에 놓지 않습니다. `.gitignore`와 `.dockerignore`에서 환경 파일·DB를 제외합니다.

일정 변경 시 기존 완료 기록을 지워서 비율을 바꾸는 방식으로 처리하지 않습니다. 일정의 적용 날짜와 제품 스냅샷을 보관합니다. 자세한 적용 시점은 저장 후 화면 안내를 기준으로 확인합니다.

제품 삭제는 보관 처리입니다. 해당 제품은 오늘의 일정·진행률·활성 성분 분석·새 알림에서 빠지고 기존 완료 기록은 읽기 전용으로 남습니다. 제품 삭제는 계정 전체의 개인정보 삭제 기능이 아닙니다.

기존 DB의 `nickname`은 이름으로 이전하고 나이는 추정하지 않아 `NULL`로 유지합니다. 스키마 버전 2로의 변경은 트랜잭션에서 수행합니다. 업그레이드 전에 구버전 서버와 워커를 종료하고 DB 디렉터리를 백업합니다. 구버전과 신버전을 같은 DB에 동시에 연결하지 않습니다. 기존 계정·세션·섭취 정보가 남아 있는 백업은 소스 코드와 분리해 접근 권한을 관리합니다.

Brevo 전환의 스키마 버전 3은 `notification_logs`에 재시도 가능 여부를 저장하는 열을 추가합니다. 기본값은 재시도 불가이며 이전 실패를 자동 재발송하지 않습니다. 기존 알림 상태와 계정·제품·복용 기록을 지우거나 새 DB로 교체하지 않습니다.

## 상한량 비교의 경계

UL 자료는 공식 출처·출처 문서 개정 연도·버전·적용 연령·범위를 [기준 자료](../lib/ul-reference.ts)에서 함께 관리합니다. 저장 전에 서버에서 로그인 사용자의 등록 제품과 후보 제품을 합산하며, 수치 UL 초과가 있으면 `safetyAcknowledged: true` 없이 저장하는 요청을 거부합니다. 브라우저 경고를 숨기는 것으로 서버 검사를 우회할 수 없어야 합니다. 대시보드 예시도 편집기 초안만 채워 공통 검사·확인 과정을 거칩니다.

사용자 입력 나이가 없거나, 성분 자료가 없거나, 성분 형태·단위가 불명확하면 비교할 수 없다는 상태를 반환합니다. 상한량이 설정되지 않은 성분을 무제한 안전으로 처리하지 않습니다. UL 이하 결과와 사용자의 경고 확인은 개인의 복용 안전·적정성·의료적 승인을 의미하지 않습니다. 성별·임신·수유·질환·약물·식사 전체를 반영한 임상 판단 기능은 제공하지 않습니다.

## 이메일과 보호자 동의

- `capture` 모드는 메시지를 DB에 저장할 뿐 외부에 발송하지 않습니다. 로컬 시연에서는 이 모드를 명시적으로 설정합니다. `.env.example`의 `brevo`는 실전 설정용이며 키·발신 주소가 빈 값입니다. 캡처 내역에도 개인정보가 포함될 수 있으므로 해당 사용자만 볼 수 있습니다.
- `brevo` 모드는 서버의 `BREVO_API_KEY`, `EMAIL_FROM`, `EMAIL_FROM_NAME`을 사용합니다. 브라우저 코드와 워커에는 메일 API Key를 전달하지 않습니다. API Key와 SMTP Key는 구분합니다.
- `EMAIL_MODE` 누락·오타, 필요한 키·발신자 누락은 알림 오류로 처리합니다. 실제 API 실패도 캡처나 성공으로 바꾸지 않습니다. 회원가입·영양제 저장 기능은 메일 설정과 분리합니다.
- 본인 알림을 먼저 처리하고, 그 이후의 추가 유예 시간과 여전히 미확인인 상태를 확인한 뒤 보호자 알림을 처리합니다.
- 보호자 알림은 유효한 주소, 활성화 상태, 명시적 동의 시각이 모두 필요합니다. 주소를 바꾸면 기존 동의를 그대로 옮기지 않습니다.
- 동의 해제나 복용 완료 후 새 알림은 전송 대상에서 제외됩니다. 이미 공급자에게 전달된 이메일을 회수하는 기능은 없습니다.
- 알림 문구는 완료 체크의 부재만 안내합니다. 미복용·결핍·의료적 위험을 추론하지 않습니다.
- 발송 요청 결과와 오류는 알림 로그에 기록합니다. API 요청 수락은 받은편지함 도착 확인과 다릅니다.

공급자 대시보드의 `Delivered`도 사용자가 메일을 열어 확인했다는 의미는 아닙니다. 받은편지함·스팸함 확인과 앱의 전송 상태는 별도로 구분해 보고합니다.

Brevo 전환 후 본인·외부 수신자·보호자의 실제 이메일 전달 검증은 아직 완료하지 않았습니다. 이전 공급자의 수신 확인을 이번 연결의 성공 근거로 사용하지 않습니다. API 접수, 공급자 전달 이벤트, 수신자의 직접 확인을 구분해 [검증 기록](VERIFICATION.md)에 남깁니다. 한 번의 수신 성공으로 모든 수신자에게 전달을 보장하지 않습니다.

Brevo 발신자 확인은 발신 주소를 제어한다는 절차이며 앱 회원의 이메일 소유권 확인을 대신하지 않습니다. 무료 Gmail 발신자는 공급자에 의해 다른 From 주소로 표시될 수 있습니다. API IP 제한이 요청을 차단하면 계정의 Authorized IPs에서 해당 서버 IP를 확인한 뒤 필요한 항목만 승인합니다. [Brevo 발신자 안내](https://help.brevo.com/hc/en-us/articles/208836149-Create-a-new-sender-From-name-and-From-email), [API IP 보안](https://help.brevo.com/hc/en-us/articles/5740111683858-Authorize-and-block-IP-addresses-for-API-and-SMTP-security)

보호자 주소의 소유권을 보호자 본인에게 다시 확인하는 이중 동의 절차는 현재 제공하지 않습니다. 사용자가 보호자에게 안내 내용을 설명하고 동의를 얻은 주소를 입력해야 합니다. 운영 확대 전 수신자가 직접 구독을 거절·철회할 수 있는 기능을 추가해야 합니다.

## 예약 실행 API

`GET /api/cron/notifications`는 로그인 세션 대신 `Authorization: Bearer <CRON_SECRET>`을 검사하는 서버 작업용 경로입니다. 충분히 긴 임의 시크릿을 만들고 앱과 워커에만 전달합니다. URL 쿼리에 시크릿을 넣지 않으며 GitHub Actions YAML에 운영 시크릿을 직접 쓰지 않습니다.

워커는 URL에 자격증명·쿼리·프래그먼트가 포함된 설정을 거부하고 HTTP 리다이렉트를 따라가지 않습니다. 로그에는 처리 건수와 HTTP 상태만 남기며 응답 본문·수신자·시크릿은 기록하지 않습니다. 종료 시 진행 중 요청을 중단하고, 실패한 스캔은 다음 주기에 재시도합니다. 서버의 영구 알림 claim과 공급자 멱등성 키로 중복 처리를 제한합니다. 배포 시 두 서비스 설정은 [배포 가이드](DEPLOYMENT.md)를 참고합니다.

개별 메일은 명백한 API 4xx 요청 거절만 60초 간격으로 총 3회까지 시도합니다. 네트워크 오류·5xx·중복 키 응답·성공 응답의 messageId 누락은 접수 여부가 불명확하므로 `failed`로 보존하고 자동 재발송을 중단합니다. 15분 넘게 미완료인 처리도 임의로 다시 보내지 않습니다. 공급자 로그에서 실제 접수·전달을 먼저 확인해야 합니다. 멱등성 키의 보관 기간이 지나도 무조건 재시도하는 방식은 사용하지 않습니다.

로그인 사용자용 `POST /api/notifications/preview`는 해당 사용자 범위에서 시연하며 cron 권한을 대신하지 않습니다. UI 시연을 이유로 다른 사람의 계정이나 보호자 주소에 임의로 발송하지 않습니다.

이 경로도 실제 알림 엔진을 사용하므로 `brevo` 모드에서는 조건에 따라 실제 발송합니다. `capture` 모드에서 만든 본인 알림을 실전 모드로 전환해 보호자 발송의 근거로 사용하지 않습니다. 실제 본인 발송의 API 접수 상태를 확인한 뒤 보호자 조건을 평가하며 받은편지함 도착을 추정하지 않습니다.

## 데이터와 인프라

- 운영은 HTTPS, 영구 디스크, 앱 프로세스 1개를 기준으로 합니다. SQLite 파일을 여러 앱 컨테이너가 동시에 공유하는 구성과 서버리스 배포는 지원하지 않습니다.
- 워커는 DB에 직접 접근하지 않고 앱 API에 요청합니다. 따라서 웹 서버에만 영구 볼륨을 연결합니다.
- DB 파일 자체는 이 애플리케이션이 암호화하지 않습니다. 호스팅의 저장소 보호·백업 접근 권한을 운영자가 관리합니다.
- 서비스와 워커를 종료한 뒤 DB 디렉터리 전체를 백업하거나 SQLite의 일관된 백업 기능을 사용합니다. 실행 중인 DB 파일 하나만 무작정 복사하지 않습니다.
- 이메일 주소, 섭취 정보, 알림 본문이 저장됩니다. DB 백업을 공개 저장소나 발표 화면에 그대로 공개하지 않습니다.
- 시크릿 유출 시 공급자 API Key와 `CRON_SECRET`을 교체합니다. 실제 비밀번호·토큰을 이슈에 첨부하지 않습니다.
- API Key를 채팅·발표 화면·공개 로그에 노출했다면 해당 키를 폐기하고 재발급한 키를 개인 `.env` 또는 배포 서비스의 비밀 설정에만 저장합니다. `.env.example`에는 빈 자리만 유지합니다.

이전 버전에서 노출된 공급자 키의 폐기를 확인한 기록은 새 Brevo 키의 보안 검증을 대신하지 않습니다. 공급자 전환 후 사용하지 않는 이전 비밀값을 환경변수에서 제거하고 Brevo 키도 동일하게 보호합니다. 키 값·키 이름·수신자 주소·공급자 메시지 ID는 공개 문서에 기록하지 않습니다.

## 현재 제공하지 않는 기능

이메일 소유권 확인·복구, 사용자 본인의 계정 삭제·데이터 내보내기, 보호자 직접 수신 거부 링크, 포괄적 감사 로그, 침투 테스트, 재해 복구 자동화는 별도 개발이 필요합니다. MVP에서 구현되지 않은 보호 장치를 제공한다고 표시하지 않습니다.

문제를 제보할 때는 사용한 화면, 재현 순서, 기대 결과와 실제 결과를 적고 비밀번호·API Key·세션 쿠키·실제 복용 기록은 제외합니다.
